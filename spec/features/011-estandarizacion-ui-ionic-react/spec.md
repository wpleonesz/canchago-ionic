# 011 · Estandarización de UI/UX con componentes Ionic React

**Estado:** en curso

## Qué hace

Define **qué** debe cambiar (y bajo qué condiciones) para que toda la interfaz móvil de `canchago-ionic` adopte de forma consistente los componentes oficiales de `@ionic/react` 8.5.0 disponibles en el proyecto, reduciendo progresivamente el HTML directo (`div`, `section`, `header`, `span`, `nav`, listas y contenedores a medida) allí donde exista un componente Ionic equivalente real, y mejorando la densidad visual en móvil (menos espacio vertical/horizontal desperdiciado, jerarquía clara, sin scroll ni overflow innecesarios).

Esta spec **no** ordena todavía ninguna implementación — eso vive en `plan.md`/`tasks.md` de esta misma feature, y su ejecución queda pendiente de aprobación explícita antes de tocar código de producción.

Alcance de pantallas/módulos reales encontrados en el repositorio (ver inventario abajo):

- Shell administrativo: `layouts/AdminLayout.tsx` (`IonSplitPane` + `IonPage`/`IonHeader`/`IonToolbar`), `features/admin/components/AdminNavigation.tsx` (menú lateral, hoy `IonMenu` + `<nav>` HTML interno), `features/admin/pages/*` (`AdminDashboardPage`, `AdminModulePendingPage`, `AdminNotFoundPage`, `AdminAccessDeniedPage`).
- Autenticación: `features/auth/components/AuthShell.tsx`, `AccountTypeStep.tsx`, `ManagerRegisterForm.tsx`, `PlayerRegisterForm.tsx`, `features/auth/pages/LoginPage.tsx`, `RegisterPage.tsx`.
- Usuarios: `features/users/pages/{UsersListPage,UserDetailPage,UserFormPage,UserProfileEditPage,OwnProfilePage}.tsx`, `features/users/components/{UserForm,UserListItem,AdminUserProfileForm,OwnProfileForm,ProfilePhotoEditor}.tsx`.
- Roles: `features/roles/pages/{RolesListPage,RoleDetailPage,RoleFormPage}.tsx`, `features/roles/components/{RoleForm,RoleListItem}.tsx`.
- Organizaciones y sedes: `features/organizations/pages/{OrganizationsListPage,OrganizationDetailPage,OrganizationFormPage,VenueFormPage}.tsx`, `features/organizations/components/{OrganizationForm,OrganizationListItem,VenueForm,VenueListItem}.tsx`.
- Solicitudes de acceso: `features/access-requests/pages/AccessRequestsPage.tsx`, `components/AccessRequestListItem.tsx`.
- Home/perfil: `features/home/components/ProfileSummary.tsx`.
- Componentes compartidos ya existentes (base de reutilización, ver "Estrategia de reutilización"): `components/common/{AppButton,AppAvatar,AppDataList}.tsx`, `components/feedback/{AppEmptyState,AppErrorState,AppSkeleton,AppConfirmDialog}.tsx`, `components/forms/{AppInput,AppSelect,AppSearchInput}.tsx`, `components/layout/AppPage.tsx`.
- Estilos: `theme/variables.css` (tokens `--app-color-*`, `--app-radius-*`, `--app-shadow-card`, `--app-content-max-width`) y un `.css` por módulo (`users.css`, `roles.css`, `organizations.css`, `admin-layout.css`, `login-page.css`, `register-page.css`, `access-requests.css`).

## Por qué

El inventario real (ver sección siguiente) confirma que, aunque la app ya usa Ionic para la infraestructura de página (`IonPage`/`IonHeader`/`IonToolbar`/`IonContent`/`IonList`/`IonItem`/`IonAlert`/`IonSkeletonText`/`IonSpinner`/`IonMenu`/`IonSplitPane`), casi todas las pantallas de negocio construyen su contenido interno con HTML directo (`section`, `div`, `header`, `span`, `nav`, `dl`/`dt`/`dd`, `fieldset`) para agrupar encabezados de página, filas de acción, bloques de detalle y controles de paginación. Esto genera:

- Inconsistencia visual entre módulos (cada `*.css` reinventa su propio patrón de "encabezado de página con eyebrow + título + acciones").
- Menor aprovechamiento de las convenciones responsive/densidad que Ionic ya resuelve (`IonGrid`/`IonRow`/`IonCol`, `IonButtons`, `IonItem` con `lines`), obligando a cada módulo a definir su propio CSS de espaciado.
- Riesgo de accesibilidad dispar (áreas táctiles, roles ARIA) al reimplementar manualmente lo que Ionic ya expone (p. ej. controles de paginación como `nav`+`span` sueltos en `AppDataList`).

El objetivo es una experiencia más compacta, coherente y verdaderamente "Ionic React", sin reescribir la lógica de negocio, navegación, permisos ni contratos ya validados por las features `001`–`010`.

## Contrato de API consumido

_No aplica._ Esta feature es exclusivamente de UI/UX y arquitectura visual. No se modifica ningún endpoint, tipo de `types/api/*`, servicio de `services/api/`, hook de `features/*/hooks/`, schema de `validation/*`, regla de permisos (`PermissionGuard`/`RoleGuard`/`AdminRoute`) ni `spec/constitution/api-integration.md`. Cualquier cambio de lógica que resultara indispensable para resolver una dependencia directa causada por la migración (por ejemplo, un componente que hoy recibe un `className` usado también como selector de test) debe quedar justificado explícitamente en `plan.md`/`tasks.md` antes de aplicarse, nunca como efecto secundario silencioso.

## Criterios visuales (medibles, sin valores CSS inventados)

_Los valores concretos (paddings, alturas, tamaños de fuente) se toman de los tokens ya existentes en `theme/variables.css` (`--app-radius-sm/md/lg`, `--app-shadow-card`, `--app-content-max-width`, colores `--app-color-*`) y de las variables CSS nativas de Ionic (`--ion-*`, `var(--ion-safe-area-*)`). Esta spec no fija px/rem nuevos; el `plan.md`/implementación deberá auditar los valores reales usados hoy en cada `*.css` de módulo antes de ajustarlos, y reutilizar/ampliar los tokens de `theme/variables.css` en vez de duplicar constantes._

- Reducir espacio vertical/horizontal no funcional en encabezados de página, tarjetas de lista (`*ListItem.tsx`) y formularios, sin reducir el área táctil mínima recomendada por las guías de accesibilidad móvil (objetivo ≥ 44×44 px para controles interactivos, igual que ya aplica `IonButton`/`IonItem` por defecto).
- Unificar el patrón "eyebrow + título + acciones" de los encabezados de listado/detalle en un único componente compartido (ver "Estrategia de reutilización"), en vez de 3 implementaciones CSS divergentes (`users.css`, `roles.css`, `organizations.css`).
- Usar `IonGrid`/`IonRow`/`IonCol` únicamente donde exista una necesidad real de distribución en columnas (p. ej. filas de acción con más de un botón, resumen de perfil con avatar + datos) — no envolver contenido de una sola columna en una grilla innecesaria.
- Eliminar scroll horizontal y superposición de elementos en los anchos de viewport móvil ya usados como referencia en el proyecto (390×844, verificado manualmente en la feature `010`; validar también en el ancho mínimo soportado por `IonSplitPane` antes de colapsar a menú overlay, `< 900px` según `AdminLayout.tsx`).
- Respetar zonas seguras (`safe-area-inset-*`, ya gestionadas por `IonHeader`/`IonContent`/`IonFooter` de Ionic) y el comportamiento de teclado nativo de Capacitor (`@capacitor/keyboard`, ya instalado) sin overlays personalizados que lo bloqueen.
- Mantener jerarquía visual: un solo `IonTitle` por `IonHeader`, encabezados de sección internos (`h2`/`h3` reales, no reemplazados por Ionic) siguiendo el mismo orden que ya usan `ProfilePhotoEditor`/`AdminDashboardPage`.

## Estrategia de reutilización

_Primero identificar y reutilizar lo que ya existe; solo crear componentes nuevos ante repetición real demostrada (ver inventario)._

- **Ya existen y se reutilizan sin cambios de API pública:** `AppButton`, `AppInput`, `AppSelect`, `AppSearchInput`, `AppAvatar`, `AppSkeleton`, `AppConfirmDialog`, `AppPage`.
- **Se ajustan internamente (misma API pública, distinto DOM interno):** `AppDataList` (paginación), `AppEmptyState`, `AppErrorState`.
- **Candidatos a componente compartido nuevo (repetición real demostrada en el inventario, ≥ 3 módulos):**
  - Encabezado de página ("eyebrow + título + acciones"), repetido en `UsersListPage`, `RolesListPage`, `OrganizationsListPage`, `*DetailPage` (users/roles/organizations) y `AdminDashboardPage`/`AdminAccessDeniedPage`/`AdminModulePendingPage`/`AdminNotFoundPage`.
  - Bloque de acciones de detalle (`IonButtons`/`IonGrid` con botones "Editar"/"Volver"), repetido en los 3 `*DetailPage`.
- El detalle de diseño de estos componentes (nombre exacto, props, ubicación en `components/layout/` o `components/common/`) se decide en `plan.md`, no en esta spec — aquí solo se ordena que existan antes de duplicar una cuarta vez el mismo patrón.
- No se duplica lógica de navegación, permisos (`PermissionGuard`/`RoleGuard`/`AdminRoute`) ni llamadas a hooks de `features/*/hooks/` — los componentes nuevos son puramente de presentación, reciben props ya resueltas por la página que los usa.

## Accesibilidad móvil

- Todo control de formulario mantiene su `label`/`aria-label` ya asociado (via `AppInput`/`AppSelect`, que ya usan `label`/`labelPlacement` de `IonInput`/`IonSelect`) — no se elimina ningún label existente al migrar el contenedor visual.
- Área táctil mínima ya provista por `IonButton`/`IonItem`/`IonMenuButton` se conserva; cualquier componente nuevo (encabezado de página, bloque de acciones) debe usar `IonButton`/`IonButtons`, nunca un `div`/`span` con `onClick`.
- Contraste: se reutilizan los tokens ya definidos en `theme/variables.css` (claro/oscuro), sin introducir combinaciones de color nuevas fuera de esos tokens.
- Estados `role="status"`/`role="alert"` ya presentes en `AppEmptyState`/`AppErrorState` se conservan al migrar su contenedor a `IonCard`.
- Ninguna interacción depende únicamente del color (los badges de estado ya combinan texto + color; se conserva ese patrón).
- Iconografía: se reutiliza exclusivamente `ionicons` (ya instalado, único paquete de íconos del proyecto) vía `IonIcon` — no se introduce ninguna librería de íconos nueva.

## Compatibilidad de dependencias

Esta feature se ejecuta contra las versiones reales instaladas hoy (`package.json`): `@ionic/react`/`@ionic/react-router` `8.5.0`, `react`/`react-dom` `19.0.0`, `ionicons` `7.4.0`, `@capacitor/*` `8.x`. No se propone ninguna API de Ionic marcada como obsoleta en esa versión, ni se agrega ninguna dependencia nueva — toda la migración se resuelve con componentes ya exportados por `@ionic/react` 8.5.0 y ya usados en el proyecto (`IonCard`, `IonGrid`/`IonRow`/`IonCol`, `IonButtons`, `IonToolbar` adicionales) o candidatos verificados como parte de esa misma versión antes de especificarlos en `plan.md`.

## Fuera de alcance

- **Cualquier cambio de lógica de negocio, validación, permisos, contratos de API o modelos de datos.** Solo se justifica un cambio mínimo de lógica si es una dependencia directa e indispensable causada por la migración visual (p. ej. un selector de test acoplado a un `className` que deja de existir), y debe quedar documentado explícitamente en `plan.md`/`tasks.md` antes de aplicarse.
- **Introducir `IonTabs`/`IonTabBar`/`IonTabButton`/`IonSegment` como navegación principal.** La app usa `IonSplitPane` + `IonMenu`; cambiar el paradigma de navegación es una decisión de arquitectura distinta, no una estandarización de componentes.
- **Introducir `IonModal`** salvo que una migración puntual lo justifique explícitamente en `plan.md` con una necesidad real no cubierta por `IonAlert`.
- **Cambiar el mecanismo de autenticación, almacenamiento seguro o navegación entre `web`/`nativo`** (features `002`/`003`) — esta spec no toca `services/auth/`, `services/storage/` ni `services/api/apiClient.ts`.
- **Rediseño de marca/paleta de colores.** Se reutilizan los tokens existentes en `theme/variables.css`; un cambio de paleta o identidad visual es una feature distinta.
- **Dominio de reservas/canchas.** No existe ese dominio en el backend ni en esta app (ver `010`); no aplica a esta migración.
- **Pruebas E2E nuevas de Cypress no ya previstas por el proyecto.** Se reutiliza la infraestructura de pruebas existente (Vitest + Testing Library); no se introduce una suite de regresión visual automatizada nueva si no existe ya en el repositorio (ver `tasks.md`, "Pruebas previstas").
