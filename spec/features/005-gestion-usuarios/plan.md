# 005 · Gestión de Usuarios — Plan

_Cómo se implementa lo descrito en `spec.md`. Debe respetar la `constitution/`._

## Enfoque

Construir la feature en las capas ya definidas por `tech-stack.md` §2-3, reutilizando todo lo que ya existe (`AppButton`, `AppInput`, `AppPage`, `RoleGuard`, `PermissionGuard`, `apiClient`, `errorMapper`, `sessionStore`) y creando solo lo que falta: tipos de `users`/`roles`/`organizaciones`, endpoints de esos módulos, hooks de TanStack Query por dominio, y un puñado de componentes genéricos que hoy son solo placeholders vacíos (`components/feedback/`, `components/forms/`, `hooks/`). El catálogo de organizaciones se resuelve con el endpoint ya existente (`GET /api/organizaciones`), sin construir la feature `organizations` completa.

## Decisiones

- **No construir la feature `organizations` completa para resolver `organizationId`** — se agrega solo un hook/endpoint de lectura mínimo (`useOrganizations`/`getOrganizations`) sobre el endpoint ya existente `GET /api/organizaciones`. Alternativa descartada: esperar a la feature backlog `006` antes de empezar `005` — se rechaza porque `005` ya estaba anticipada como la siguiente feature en el roadmap y no depende de CRUD de organizaciones, solo de listarlas para elegir una.
- **Normalizar el envelope `{organizations, meta}` dentro de `services/api/endpoints/organizaciones.ts`, no en el hook ni en el componente** — mantiene la responsabilidad de conocer las excepciones de envelope documentadas en `api-integration.md` §7 dentro de la capa `services/api/`, tal como exige `tech-stack.md` §4 (el interceptor de response ya normaliza envelopes ahí). Alternativa descartada: normalizar en el interceptor global de Axios — se descarta porque el interceptor no puede distinguir de forma genérica `{organizations}` de un futuro `{venues}`/`{data}` sin acoplarse a cada endpoint; se prefiere normalizar en el endpoint específico, que sí conoce su propio contrato.
- **No ofrecer roles globales (`Administrador`, `Futbolista`) en el selector de roles** — no es una elección de diseño de esta feature, es un reflejo de que `GET /api/roles` no los expone (ver quiebre documentado en `spec.md`). Se decide no "rellenar" ese hueco con una lista hardcodeada de roles globales conocidos, porque eso violaría directamente el requisito de que los roles nunca estén codificados estáticamente en Ionic — se prefiere dejar la limitación visible y documentada antes que simular una capacidad que el backend no sostiene.
- **`AppDataList`/tabla paginada genérica en vez de una tabla ad-hoc dentro de `features/users/`** — se anticipa que `006` y `007` necesitarán el mismo patrón de lista paginada con búsqueda; construirla en `components/common/` evita duplicar el patrón tres veces. Alternativa descartada: construir el listado inline en `UsersListPage.tsx` y refactorizar después — se descarta porque el propio `tech-stack.md` §3 ya reserva la ubicación genérica, así que no hay motivo para posponerlo.
- **`staleTime` corto (no cacheado agresivamente) para `useUsers`/`useUser`** — a diferencia de un catálogo de roles/permisos (que cambia poco), la lista de usuarios es un dato administrativo que otros admins pueden modificar en paralelo; se prioriza frescura sobre reducir requests. `useRoles` sí puede usar un `staleTime` más largo (catálogo relativamente estable dentro de una sesión), invalidado explícitamente si esta misma feature permite editar roles (no lo hace — eso es `007`).

## Riesgos

- **La protección contra escalamiento de privilegios depende de un backend que hoy no la implementa** — mientras `canchago/spec/features/015-bootstrap-super-admin/` no esté implementada, ocultar roles `isSystem` en la UI es solo UX, no seguridad real. Mitigación: como los roles globales ya son invisibles vía `GET /api/roles` (ver quiebre documentado), el riesgo práctico hoy es bajo — pero se documenta explícitamente en `api-integration.md` y no se marca esta feature como "cerrando" ese riesgo.
- **`organizationId` obligatorio pero sin forma de saber "mi organización"** — el `SessionUser` no expone a qué organización(es) pertenecen los roles del admin actual (`UserRole.organizationId` no se refleja en `/api/auth/session`). Mitigación: el picker de organización siempre lista el catálogo completo (`GET /api/organizaciones`) sin preseleccionar nada por defecto; se documenta como gap en `api-integration.md` (propuesta futura: que `/api/auth/session` incluya el alcance de organización del usuario).
- **`orderBy=name` y `active=false` son trampas reales del backend** — un desarrollador futuro que agregue una opción de orden/filtro "obvia" sin releer este documento podría reintroducirlas. Mitigación: los valores permitidos se definen como listas blancas explícitas y comentadas en `src/validation/users.ts` y en `src/features/users/components/UserListItem.tsx`/el componente de filtros, citando este documento.
- **`POST /api/users/:userId/roles` sin control de duplicados en el backend** (confirmado: `addRoleToUser` no verifica si el par `userId`/`roleId` ya existe) — asignar el mismo rol dos veces desde la UI (p. ej. por un doble clic que burla el `isLoading` del botón) crearía dos filas `UserRole`. Mitigación: el hook `useAssignUserRoles` deshabilita el control mientras la mutación está en curso y el selector de roles excluye del catálogo los roles que el usuario ya tiene asignados (comparando contra `useUser(userId).data.roles`).
- **Backend sin rate limiting conectado** (`rate-limiter-flexible` instalado pero no usado en ningún endpoint, confirmado) — esta feature no puede mitigar esto desde el cliente; se documenta como gap de backend en `api-integration.md`, no se implementa un throttling artificial en el cliente que daría una falsa sensación de protección.
