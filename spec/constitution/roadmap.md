# Roadmap

_Orden y estado de las features. Cada entrada apunta a su carpeta en `features/`._

## Hecho ✅

1. **001 · Fundación del proyecto** — Ionic React 8 + TypeScript estricto + Capacitor 8 (Vite), estructura de carpetas de `tech-stack.md` §3, ESLint + Prettier, cliente Axios único (`services/api/apiClient.ts`, `withCredentials: true`), taxonomía de errores tipada (`services/api/errorMapper.ts`), logger propio con redacción (`services/telemetry/logger.ts`), storage no sensible sobre `@capacitor/preferences`, `QueryClientProvider` + `IonReactRouter` + tema claro/oscuro, componentes base `AppButton`/`AppPage`, Vitest con pruebas de humo (9 tests). Migrado a Yarn (unifica con el backend). Plataformas nativas Android e iOS agregadas y validadas con builds headless reales (`gradlew assembleDebug` → `BUILD SUCCESSFUL`; `xcodebuild` para simulador → `BUILD SUCCEEDED`). App exclusivamente nativa — nunca web/PWA; `yarn dev` es solo atajo de desarrollo. Sin pantallas de negocio ni login real — eso empieza en `002`. Ver `spec/features/001-fundacion-proyecto/`.
2. **002 · Autenticación** (alcance navegador/dev) — Login/logout/sesión real contra Keycloak vía proxy de Vite (mismo origen en dev, sin tocar el backend). `ProtectedRoute`/`PublicRoute`/`RoleGuard`/`PermissionGuard` implementados y probados. **Validado con Chrome headless real contra el backend corriendo local** (Postgres + Keycloak + Next.js): login, identidad real en pantalla, persistencia tras recarga, logout, deep-link protegido, guards de rol/permiso con un usuario real sin permisos. Se encontró y corrigió un bug real de TanStack Query en el logout (`clear()` → `resetQueries`). Ver `spec/features/002-autenticacion/`.
3. **003 · Autenticación nativa (Android/iOS empaquetados)** — Formulario nativo de usuario/contraseña (`AppInput` + React Hook Form + Zod) que llama a `POST /api/auth/mobile/login` y recibe `Authorization: Bearer`. **Revisado el mismo día**: se implementó primero con Authorization Code + PKCE + navegador in-app (validada parcialmente), pero el usuario pidió reemplazarla por un formulario nativo (estilo Facebook) — decisión de producto que implicó Resource Owner Password Credentials del lado del backend, confirmada explícitamente por el usuario tras explicarle el riesgo. Token guardado en `@aparajita/capacitor-secure-storage`. **Validado de punta a punta en un emulador Android real** (no un mock): login real, identidad real en `/home`, logout real, sesión persistente tras matar y reabrir la app. En el camino se encontraron y corrigieron 6 gaps de infraestructura reales (Mixed Content, App Transport Security, `usesCleartextTraffic`, CORS ausente en el backend, `withCredentials` incompatible con CORS abierto, header `X-Correlation-ID` fuera de la lista de CORS) — ninguno evidente por adelantado, todos aparecieron probando contra el sistema real. Ver `spec/features/003-autenticacion-nativa/spec.md` para el detalle completo.
4. **004 · Rediseño visual de login y home** — Login web/dev y nativo modernizados con `AuthShell`, tokens semánticos claro/oscuro, formularios accesibles y layout adaptable inspirado en una jerarquía visual familiar sin copiar marcas externas. `Home` convertido en panel de cuenta con iniciales, identidad, roles, estado vacío y resúmenes condicionados por `RoleGuard`/`PermissionGuard`, sin datos ni accesos ficticios. Sin cambios de API, autenticación o dependencias. Validado con lint, TypeScript, 27 pruebas, build web, Capacitor sync y builds headless Android/iOS. Ver `spec/features/004-rediseño-login-home/`.
5. **005 · Gestión de usuarios** — CRUD administrativo completo (listar con paginación remota, búsqueda con debounce, filtro activos/todos; crear; ver detalle; editar; desactivar) y asignación/remoción de roles de organización, consumiendo el contrato real de `canchago` (`/api/users*`, `/api/roles`, `/api/organizaciones`). El bloqueo original de esta feature (bug de permisos `users.*` vs `usuarios.*`) **se verificó resuelto en el código real del backend** — ya no aplica. El catálogo de roles/organizaciones se obtiene siempre en vivo, nunca hardcodeado; los roles globales (`Administrador`, `Futbolista`) no son seleccionables porque el backend no los expone vía `GET /api/roles` — la app no puede crear ni promover super admins, coherente con `canchago/spec/features/015-bootstrap-super-admin/`. La protección real contra escalamiento de privilegios sigue dependiendo de que esa feature de backend se implemente (hoy la UI solo oculta esa opción). Componentes genéricos nuevos reutilizables: `AppDataList`, `AppSearchInput`, `AppSelect`, `AppEmptyState`, `AppErrorState`, `AppSkeleton`, `AppConfirmDialog`, `useDebounce`. Integrado bajo `/admin/users` (shell administrativo de la feature `006`). Validado con lint, typecheck y build limpios, y 53 pruebas verdes (15 nuevas). Ver `spec/features/005-gestion-usuarios/`. **Corrección (2026-09-04):** en `UserDetailPage` (`/admin/users/:userId`), asignar el primer rol a un usuario que aún no tenía ninguno era imposible — `organizationId` solo se derivaba de `user.roles[0]`, así que sin roles previos quedaba `undefined`, `UserRolesEditor` nunca cargaba el catálogo (`useRoles` con `enabled: Boolean(organizationId)`) y la pantalla no ofrecía ninguna forma de elegir la organización. Se reutilizó `OrganizationPicker` (ya existente en el formulario de creación) para mostrarlo solo cuando el usuario no tiene ningún rol con organización real; una vez asignado el primero, se sigue derivando como antes. El backend (`POST/DELETE /api/users/{userId}/roles*`) se verificó correcto (idempotente, transaccional, con guardias de escalamiento) — el bug era exclusivamente de esta pantalla. 2 pruebas nuevas en `UserDetailPage.test.tsx`; lint/typecheck/build limpios, suite verde salvo el mismo fallo preexistente y ajeno de `UserForm.test.tsx`.
6. **007 · Edición administrativa del perfil de usuario** — Pantalla dedicada bajo `/admin/users/{userId}/edit` para modificar únicamente nombre y apellido, con identidad/estado informativos, validación Zod, prevención de doble envío, aviso por cambios pendientes, estados controlados e invalidación selectiva de caché/sesión. Consume el nuevo subrecurso backend `/api/users/{userId}/profile`, protegido por `users.read`/`users.update`, lista blanca estricta, guard de usuarios de sistema y concurrencia optimista. Sin migraciones, avatar ni exposición de credenciales/RBAC. Ver `spec/features/007-edicion-perfil-usuario-administracion/`.

7. **009 · Perfil ampliado y autogestión** — Ruta `/admin/profile` para toda sesión autenticada, con celular y enlaces opcionales, validación Zod, concurrencia optimista y cambios pendientes. Permite seleccionar, previsualizar, reemplazar y eliminar avatar de hasta 2 MiB; lo descarga autenticado como Blob y reutiliza `AppAvatar` con fallback de iniciales. Validado con lint, TypeScript, 58 pruebas, build web, Capacitor sync y APK Android debug. Ver `spec/features/009-perfil-ampliado-autogestion/`.
8. **012 · Catálogo de Permisos** — `/admin/permissions` deja de mostrar el placeholder "Módulo previsto" y pasa a listar el catálogo real de `GET /api/permisos` (código, módulo, acción, descripción), con búsqueda remota y paginación vía `AppDataList` — de solo lectura, sin CRUD. Reutiliza tipos, cliente y componentes ya existentes (`PermissionDto`, `getPermissions`, `AppDataList`, `AppSearchInput`); único código nuevo: un hook de consulta paginada (`usePermissionsCatalog`, distinto de la infinite query `usePermissions` que ya usa el selector de permisos de un rol) y la pantalla/fila de presentación. `yarn lint && yarn typecheck` y `yarn build` limpios; suite de pruebas verde salvo el mismo fallo preexistente y ajeno de `UserForm.test.tsx` ya documentado arriba (008/011). No se verificó manualmente contra un backend real corriendo (sin Postgres/Keycloak disponibles en este entorno); el contrato se verificó leyendo el código real de `canchago`. Ver `spec/features/012-catalogo-permisos/`.

## Siguiente 🔜

- **013 · Sincronización offline de contacto de perfil (Outbox)** — Ejemplo didáctico de offline-first con patrón Outbox sobre SQLite nativo (`@capacitor-community/sqlite`) para editar celular/enlaces sociales en "Mi perfil" sin conexión, con sincronización automática al reconectar, backoff exponencial con jitter, y manejo explícito de conflicto (409) sin sobrescritura silenciosa. Reutiliza el `PATCH /api/profile` ya existente (feature `009`) sin tocar el backend. `yarn lint && yarn typecheck && yarn test && yarn build`, `yarn cap:sync` y un build headless real de Android (`gradlew assembleDebug` → `BUILD SUCCESSFUL`, con `@capacitor-community/sqlite`/`@capacitor/network` empaquetados) pasan limpios. Falta la verificación manual interactiva en emulador (pérdida de conexión, sincronización, conflicto) — requiere el backend `canchago` corriendo, no levantado en esta sesión por ser un cambio de alcance mayor no solicitado — antes de mover a "Hecho". Ver `spec/features/013-sincronizacion-offline-perfil/`.

- **Gestión dedicada de permisos de roles (backend 020, en cierre)** — Nueva ruta `/admin/roles/:roleId/permissions` con catálogo real paginado/buscable, selector agrupado compartido, resumen de altas/bajas, reemplazo atómico, conflicto 409, dirty warning e invalidación de sesión. Lint/typecheck, 9 pruebas focalizadas y build web pasan; falta integración/E2E y la suite global conserva el fallo preexistente de `UserForm.test.tsx`. Ver `canchago/spec/features/020-gestion-permisos-roles-administracion/`.

- **010 · Gestión de organizaciones y sedes (administración)** — Spec creada, sin implementar. Pantalla administrativa bajo `/admin/organizations` (reemplaza el placeholder de solicitudes de acceso, reubicado como subruta) para listar/consultar/crear/editar organizaciones y, desde el detalle de cada una, gestionar sus sedes (`Venue`). Consume el CRUD ya "Hecho" del backend (`canchago` feature `004`). Documenta explícitamente gaps reales de backend sin cerrar (IDOR entre organizaciones en el CRUD de sede individual, sin scope de alcance en operaciones por ID, sin concurrencia optimista, sin unicidad real de nombre de organización, sin auditoría, sin conteo de sedes) que esta feature no puede resolver por sí sola. Ver `spec/features/010-gestion-organizaciones-sedes/`.
- **Gestión administrativa de roles (contraparte backend 018, en cierre)** — Módulo `/admin/roles` implementado con listado remoto por organización, búsqueda/filtro/orden/paginación, detalle, formulario compartido create/edit, catálogo real de permisos, roles de sistema read-only, dirty warning y manejo de conflicto 409. Lint, typecheck, pruebas específicas y build web pasan; no se mueve a “Hecho” hasta completar los gates integrados/E2E y el cierre backend de 018.
- **008 · Registro público de usuarios** — Implementada y verificada en navegador (Playwright contra `yarn dev` real, Keycloak/Postgres reales): `/register` con selector Futbolista/Gestor de Cancha, ambos flujos de registro, confirmación distinta por tipo de cuenta, enlace desde `/login`, prellenado de email en el login nativo, y el nuevo módulo administrativo `/admin/organizations` (solicitudes de acceso: listar, aprobar, rechazar, con `AppConfirmDialog`) — reemplaza el placeholder de organizaciones, ahora protegido por `organizaciones.manage` en vez de `organizaciones.read`. 30 pruebas nuevas, lint/typecheck/build limpios. Un bug real de layout se encontró y corrigió durante la verificación manual (`AccessRequestListItem`: badge + botones en `slot="end"` se cortaban fuera de un viewport móvil angosto). **No se marca "Hecho" todavía**: falta la verificación en un emulador/dispositivo Android o iOS real (`yarn android`/`yarn ios`) — el único target real de esta app, per `tech-stack.md`; el navegador solo valida la lógica. Ver `spec/features/008-registro-publico/tasks.md`.
